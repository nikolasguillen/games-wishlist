# Tasks: Search Dropdown on Wide Windows

**Input**: Design documents from `specs/022-search-dropdown-wide/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/ui-contract.md](./contracts/ui-contract.md), [quickstart.md](./quickstart.md)

**Tests**: Two new JVM test files, for the pure rules (the constitution asks for a test on new mapper logic): the panel's reading order (T007) and the highlight moves (T022). Nothing else is tested automatically: there is no ViewModel, state or mapper change that feeds the overlay, and the existing suites (`SearchViewModelTest` included) must stay green untouched. Presentation, keyboard, mouse and focus are verified with the quickstart, because the project has no Compose UI test harness and adding one is out of scope.

**Organization**: Tasks are grouped by user story. US1, US2 and US3 are all P1 and together are the MVP. The wide window starts using the dropdown at T019 (the end of US1), and from there US2 and US3 refine how it behaves, so the three should land before the branch is merged. US4 (P2) adds no code of its own unless the verification finds something.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task)
- **[Story]**: US1 (the dropdown), US2 (keyboard and mouse), US3 (closing without losing the text), US4 (resizing across 840dp)

## Path conventions

All paths are relative to the repository root. Two shorthands are used below:

- `FS` = `feature/search/src/commonMain/kotlin/com/nikolasguillen/questlog/feature/search`, so `FS/components/SearchBars.kt` is `feature/search/src/commonMain/kotlin/com/nikolasguillen/questlog/feature/search/components/SearchBars.kt`.
- `FT` = `feature/search/src/androidHostTest/kotlin/com/nikolasguillen/questlog/feature/search`.

Commands use the Unix wrapper (`./gradlew`); on Windows use `.\gradlew.bat`. The iOS tasks are macOS-only, and anything that needs a window to look at is reported as unverified rather than assumed when it cannot be run.

Project rules that apply to every task: one composable unit per file in `components/`; `internal` by default; spacing from `MaterialTheme.spacing`, never a `dp` literal for a gap (a layout dimension is a named constant beside its code, the precedent of `SUGGESTION_COVER_WIDTH`); colors from `MaterialTheme.colorScheme` / `MaterialTheme.appColors`; the feature's own `Res` is imported bare and each resource needs its own import; a cross-module `Res` is aliased `CoreUiRes`; every new composable gets a `private` `@QuestLogPreviews` preview wrapped in `QuestLogTheme { }`, plus a `@Preview(widthDp = 720)` where width matters (a popup itself cannot be previewed, so it is exempt: its panel is previewed instead); comments and KDoc in English; never edit anything under `build/generated/`. **No new string is added**: every label already exists.

## Implementation Strategy

### MVP first (US1 + US2 + US3)

1. Phase 1 and Phase 2: the groundwork, with the compact overlay unchanged and the build green at every step. The wide window still shows today's screen until T019.
2. Phase 3 (US1): the panel and its content. T019 switches it on; **stop and validate** with the mouse on desktop (T020) before building on it.
3. Phase 4 (US2) and Phase 5 (US3): the keyboard, the mouse hover and the closing rules. These three P1 stories together are the feature the spec asks for, so merge after US3, not after US1.
4. Phase 6 (US4) and Phase 7: prove the boundary, the compact path and the other platforms.

### Incremental delivery

- Apart from the one compile step T009-T013, every task leaves the app building and the suites green, so the work can stop at any checkpoint. Until T019 nothing visible changes. Between T019 and T026 a wide window already has a working click-driven dropdown (Material's own handling closes it on an outside click or a back press).
- US4 adds no code unless its verification finds a fault.

### Notes

- Two new test files, no ViewModel, UI state, event, domain, data, network or database change, no new string, and no new module edge or library. Only `:feature:search` changes; `:shared` already passes `isWideWindow`.
- Commit after each task or small group, with `type(scope): subject` messages (scope `search`, or `docs` for T033), first line at most 72 characters, and a body that explains why when it is not obvious. **No `Co-Authored-By` trailer and no other attribution**: the owner's global rule, which the commit hook's format does not require.
- The Material 3 `ExpandedDockedSearchBarWithGap` is experimental in the JetBrains artifact; if a task shows that it behaves differently on a platform than research R2 recorded, say so and let the owner choose between it, the non-gap `ExpandedDockedSearchBar` (a one-line swap) and a custom panel, rather than switching alone.
- If a task turns out to need a change outside the files it names, or in the compact overlay's behaviour, stop and say so before widening it: the owner asked for presentation only, and the compact overlay must keep working exactly as today.
